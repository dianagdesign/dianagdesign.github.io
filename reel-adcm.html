The problem

The data existed. The link back to the patient didn’t.

Decades of genomic and imaging data sat in the catalog, but the sample-to-patient link lived in private spreadsheets. Without it, the data was invisible to researchers, and to the AI tools being built on top.

DatasetGenomic, RNA, imaging
Team’s sample labelIn a private spreadsheet
SampleThe lab’s official record
PatientNeeded to find the data

The turn

A prototype got a stalled project moving

I built a working prototype of the MVP so leadership could see the workflow, and they approved the build after seeing it run. When the scope grew to include the core labs, the labs signed on after seeing a prototype I built for them. Four developers now build from it.

What I designed

One catalog, three audiences

Labs register and deliver the data, study leads decide what others can find, and a review group decides how long it stays private. The animation above follows the lab and the study lead. This is the review group’s view, where the stakes are highest.

Key decisions

Four calls that shaped the product

01
Boundary

Cut scope, keep the safeguards

When leadership asked for a faster turnaround, the engineering lead asked me to document what we could scale down. The team split the work into two releases and held one line: nothing reaches the catalog without validation.

  • Validation before anything reaches the catalogKept
  • Save and resumeKept
  • In-app messagingEmail list instead
  • AI column mappingLater release
  • Custom privacy periodsDefault only
  • Full study-lead dashboardGaps only
02
Legibility

AI that can wait until it is trusted

I designed AI column mapping with plain High, Medium and Low labels. Release 1 launches without it, and the same screen works by hand, so AI can be added later without new screens.

03
Control

One source of truth, one question per row

Four options made every reviewer a data owner. I cut it to one question, so the catalog stays the single source of truth and every decision can be audited.

04
Legibility

Send problems back, never hold them

I built and tested the project-based model the team adopted. Each project is accepted or sent back on its own, with problems marked in the spreadsheet people already work in.

Valid project
Upload→Validate→Accepted
Flagged project
Upload→Validate→Marked in their spreadsheet→Re-upload

Design to build

The design became the source engineers build from

Tokens, components and written rules live in one repo, and engineers point their AI coding tools directly at it.

In the app’s codebaseThe lead developer pulled the styles and naming straight from the repo into the app’s codebase.
A second tool, in useI also designed a separate tool for a research support team in a month, prototyped in code so the developers could build it quickly and faithfully. It helps them find reusable patient data across studies. It’s in use, and the team calls it “the Diana tool.”
One design repo, two buildsThe design repo now serves two Mayo builds, so developers on both build from the same components.
